# Cog

This is a combined record of my Cog ideas through January 20, 2026. The idea
started under the name Conveyor, spent some time as Machina, briefly became
ARP, and later came back to Cog. The names and API changed, but the main goal
stayed the same.

The source material lives in the
[`skeswa/notes`](https://github.com/skeswa/notes) repo. Links later in this file
point to the journal entries behind each stage of the design.

Cog is a signals design for application state. It should feel like normal
variables and functions, while still giving the app one clear state graph,
controlled writes, small UI updates, and a useful history of every change.

This is a design dump, not a settled spec. When two notes disagree, I call out
the change instead of pretending there was always one answer.

## Why Cog exists

Cog grew out of Ditto Subject/BLoC, a state system built for a large Flutter web
app. Ditto Subject/BLoC borrowed ideas from NgRx and Flutter's BLoC pattern. Its
main value was the `Subject`, which was much like an Rx `BehaviorSubject`: it
held a current value and had a stream of later values.

The state layer was made from many small facts. Some facts were written by the
app. Other facts were pure functions of those facts. If `temperature` and
`isRaining` are inputs, `isNiceOutside` can depend on both. A change flows
through a directed graph until every fact is up to date. Cycles are not
allowed.

That model did several things well:

- Each fact had one source of truth.
- Dependencies made cause and effect easier to follow.
- Writes were limited to the BLoC that owned the state. Outside code could only
  ask for a change by sending an action.
- Small subjects let Flutter rebuild only the widgets that needed a new value.
- The system was in a good position to support Redux-style history and debug
  tools, even though those tools were never finished.

But the system was hard to use.

Before a developer could add a piece of state, they might need a BLoC library,
a BLoClet for one entity, glue between the BLoC and BLoClet, and a provider.
People often skipped the system and made their own local state machines. That
split state across the app and weakened the single-source-of-truth model.

The Subject API had also split into too many types. There were source, static,
stream, map, test, and derived subjects for several fixed numbers of inputs. A
developer had to know which class fit each case. There was little help for
making that choice.

Streams caused a deeper problem. A long chain of subjects updated one step at a
time. A widget could read one subject after it changed and another before it
changed. Two parts of the screen could then show facts from different moments.
I called this the telephone problem. A state graph should present one sound
snapshot, not expose a half-finished wave of updates.

The name BLoC also made people think the system was only for business logic.
They did not use it for UI state such as focus, animation timing, or a Flutter
`GlobalKey`. On top of that, BLoCs lived at the root of the widget tree. State
that should have been local became global, and a global BLoC could not reach a
smaller BLoC below it.

Cog tries to keep the good parts and remove that friction.

## Design goals

The API should be simple enough to read without first learning a state
management dialect. Adding state should look close to declaring a variable and
writing a function.

The computer should handle IDs, registration, debug wrappers, and other repeated
work. Early notes put this work in generated files. Later notes looked for ways
to need less generation in the first place.

State should be allowed anywhere. Global state can live in a top-level library.
Feature state can live in a feature file. Short-lived state can live near a
widget. A developer should not have to hoist every state object to the app root.

The surface should feel familiar to people who have used hooks, Riverpod,
Jotai, Recoil, or query libraries. The useful ideas are small declarations,
automatic dependency tracking, keyed state families, local subscriptions, and
query-like caching.

Cog should also keep the safety of the old system:

- One source of truth for each fact.
- A directed state graph with no cycles.
- Writes through known and named paths.
- A coherent snapshot after each turn of the graph.
- Fine-grained updates for Flutter.
- Enough runtime information to explain why any value changed.
- Clear rules for async work, stale results, loading, and failures.

The three words in the latest note are a good test for every choice:
simplicity, correctness, and performance.

## The original machine metaphor

The Conveyor version used a mechanical machine as its mental model.

A cog holds one fact. A cog can be a source value, or it can derive its value
from other cogs.

An op is a function the application calls to ask for a state change. Early
Conveyor notes called these actions, maneuvers, and levers at different points.
The later `Op` name is shorter and states the job well.

A mechanism watches cogs and performs work outside the state graph. It fills
the same role as an NgRx effect. Sending a notification, starting a timer, or
calling another system after a change belongs in a mechanism.

A machine is a file that groups cogs, ops, and mechanisms for one area, such as
weather or authentication. At first a machine was also a class instance. By
July 2023, the class was dropped. The file remained useful as an organizing
idea, but it did not need a runtime object.

The Conveyor was the runtime that owned values, scheduled updates, registered
mechanisms, and exposed the state graph. By November 2023 this runtime was
called `Cogtext`, a mix of Cog and context.

The words changed like this:

| Job | Early name | Later shape |
| --- | --- | --- |
| One state fact | Subject, then Cog | `Cog<T>` |
| A family of facts by key | Scoped or keyed Cog | `CogBox<T, K>` |
| A named write | Action, maneuver, lever | `Op`, then a method on `Cogtext` |
| A side effect | Mechanism | `Mechanism`, or a `Cogtext.run` reaction |
| A feature group | BLoC, then Machine | A plain Dart library or file |
| The runtime | Conveyor | `Cogtext` |

`Cog` is the one name that survived most of the sketches. Even that was not
fully settled. In September 2023 I considered `Arp`, short for Algebraic effect,
Reactive state, Primitive, because Cog felt a little forced.

## Cogs and the state graph

The smallest stable split is between manual and automatic cogs.

A manual cog stores state that an op can write. It is a source input to the rest
of the graph.

```dart
late user = Cog.man<User?>((c) => null);
```

An automatic cog computes a value. Its controller reads other cogs, and those
reads become dependency edges.

```dart
late usersZipCode = Cog((c) {
  return c.get(user)?.zipCode;
});
```

Earlier versions called these `Cog.simple` and `Cog.complex`, then `Cog.man` and
`Cog.auto`. One June 2023 sketch added `Cog.proc` for an async procedure. By
November, sync and async automatic cogs shared the same `Cog` constructor.

The callback argument also gained a name. `CogController` is the `c` in a cog
definition. It gives the computation access to other cogs, its current value,
its key, and any lifecycle tools the final API supports.

Reads were named `use`, `interlock`, `link`, and finally `get`. The core idea did
not change: reading through the controller tells the runtime both which value is
needed and which edge to add to the graph.

This is why the June note says that getting a cog value should be hard. A free
global getter would make it easy to hide dependencies and bypass the runtime.
Later sketches do use `get`, but it is `c.get(...)` inside a known Cog or
`Cogtext` context. The guardrail stayed even as the spelling got simpler.

Derived cogs can stop early. A weather cog might read `isSunny` first and avoid
reading the UV index when it is cloudy. The dependency set may therefore change
from one run to the next. Early drafts marked a link as `temporarily: true` so
the runtime could remove it if the next run did not use it.

This area needs firm rules. Later notes call for lints against conditional hook
calls and early exits in custom hooks or automatic cogs. That suggests some
drafts depended on hook call order, while other drafts treated links as a
dynamic set. The final design must choose one model. Dynamic dependencies fit
the examples better, but they need stable identity and careful cleanup.

An automatic cog has an initial or fallback value. Sync cogs use it before the
first run. Async cogs can expose it while work is pending. The API moved from a
positional fallback to an `init` callback, which allows a fresh value for each
runtime or key.

One sketch also lets a cog return `c.curr`. That keeps the current value and
filters out a result without causing a new change. A custom `equals` function
can do a related job by deciding when two values count as the same.

## Keyed state

Many apps need the same kind of state for many entities. Weather is not one
value. It is one value per ZIP code. The first Conveyor draft called this
context. Then it called it scope. Both forms became awkward because a simple cog
had to declare which scopes it cared about, and callers had to pass the right
scope through several layers.

The March 31, 2023 notes replaced scope with a typed key.

A keyless cog has the key type `void?` and acts like a single global value. A
keyed cog has one value per key. When a keyed cog reads another keyed cog, its
key passes through by default. A caller only names the key when it crosses to a
different entity or goes from keyless state into keyed state.

Crossing that boundary without a key should be an error. Silent use of the
wrong entity would be worse than a little extra syntax at the boundary.

That allows a chain like this:

```dart
final weather = Cog<Weather?>.auto(
  null,
  (c) async {
    final zipCode = c.key;
    final service = c.use(weatherService);
    return service?.weatherFor(zipCode: zipCode);
  },
  key: ZipCode,
);

final isSunny = Cog.auto(
  false,
  (c) {
    final weather = c.use(weather);
    return weather?.isSunny ?? false;
  },
  key: ZipCode,
);
```

The ZIP code flows from `isSunny` to `weather` without being repeated. A
keyless cog such as `isNiceOutsideAtCurrentLocation` can read the current ZIP
code and then select `isNiceOutside` with that explicit key.

Typed keys also support a changing set of dependencies. A vacation cog can loop
over ZIP codes and link to one `shouldWearHat` value for each code. On the next
run, links for removed ZIP codes can be dropped.

The 2026 version makes the family more visible by using `CogBox<T, K>`:

```dart
late temperature = CogBox.man<double?, ZipCode>((c, zipCode) => null);

late isNice = CogBox<bool, ZipCode>((c, zipCode) {
  final temp = c.get(temperature[zipCode]);
  return temp != null && temp > 68.0;
});
```

Indexing the box returns the cog for one key. This reads more plainly than
putting a `key:` type on every `Cog` declaration. It also makes the difference
between one value and a family of values hard to miss.

The notes do not settle when an unused keyed value should be removed. A final
design needs rules for disposal, cache size, and whether a key can stay alive
because another cog still depends on it.

## Writes and ops

Only manual cogs should accept writes. The name of the write changed several
times: `turn`, `advance`, `write`, and `ManualCog.set` all appear in the notes.
Each form takes the runtime controller, the cog, an optional key, and either a
new value or a function of the old value.

The first design enforced ownership with BLoC classes. Cog looked for a lighter
rule. The July 2023 idea was to let a manual cog be written only from the Dart
library that declares it. A custom lint would reject `ManualCog.set` anywhere
else. That removes the `Machine` class while keeping a clear write boundary.

The November version moved writes onto `Cogtext` and proposed another lint:
`Cogtext.write` may only appear inside an extension on `Cogtext`. Named app
functions then look like ordinary methods.

```dart
extension WeatherOps on Cogtext {
  Future<void> updateHeatAdvisory(ZipCode zipCode) async {
    final service = read(weatherService);
    final advisories = await service.advisoriesOf(zipCode: zipCode);

    write(
      isHeatAdvisoryInEffect,
      key: zipCode,
      to: advisories.any((item) => item is HeatAdvisory),
    );
  }
}
```

This is close to the original op idea without needing command objects. Outside
code can call `cogtext.updateHeatAdvisory(zipCode)`, but it cannot write the
advisory cog by accident.

The June sketch made ops first-class values:

```dart
final refreshWeather = Op<({ZipCode zipCode})>.async((c, args) async {
  final temp = await getTheTempOutsideInC(args.zipCode);
  temperature.set(c, key: args.zipCode, (_) => temp);
});
```

A first-class async op could expose useful state of its own. `op.live` was a cog
containing the calls now in flight, and `op.latestFailure` held the arguments
and error from the latest failed call. This would give buttons and error views
standard loading and failure state without hand-written cogs for every request.

The notes never choose between first-class `Op` values and plain `Cogtext`
extension methods. They can fit together. An extension method is the app-facing
API, while `Op` can be the lower-level wrapper when call tracking, concurrency,
or debug history is needed.

## Mechanisms and reactions

Derived state should stay inside cogs. Work that changes the outside world
belongs in a mechanism. A mechanism can watch a cog, read other state without
linking it as derived state, call a service, and request later writes through an
op.

Examples in the notes include:

- Check the weather when the current ZIP code changes.
- Notify the user when the weather becomes nice.
- Refresh the current location every hour.
- Print a value when an automatic cog changes.
- Watch the in-flight calls for an async cog or op.

Mechanisms need lifecycle cleanup. The class-based draft had `operate()` plus
`disposeLater()` for timers and subscriptions. The file-based draft registered
all mechanisms when the runtime started. A proposed lint banned `late`
mechanisms so registration could not depend on accidental access.

The early runtime made a useful split between `read` and `watch`. `read` gets a
value without making a subscription. `watch` returns updates and, by default,
also emits the current value right away. A lazy watch waits for the next change.

By 2026, the same idea appeared in a smaller form:

```dart
Cogtext.run((c) {
  final shouldGo = c.get(shouldUserGoOutside);

  if (shouldGo) {
    print('Go!');
  }
});
```

`Cogtext.run` is a reaction. It tracks the cogs read during the callback and
runs again when they change. A full `Mechanism` type may still be useful for
names, lifecycle, testing, and debug output, but the small form is enough to
state the main behavior.

## Async cogs and scheduling

Async state was part of Cog from the first sketch. One cog used an async
generator to update the current hour. Others fetched weather or a UV index.

An async dependency can change again before its current work finishes. The
March 2023 design named four scheduling choices using Rx terms:

| Cog scheduler | Rx-style meaning | Behavior |
| --- | --- | --- |
| `allAtOnceInOrder` | `concatMap` | Queue runs and finish them in input order. This was the proposed default. |
| `allAtOnce` | merge or free-for-all | Let runs overlap. |
| `oneAtATime` | exhaust or ignore | Ignore new requests while one run is active. |
| `latestOneAtATime` | `switchMap` | Stop caring about the old run and keep the latest request. |

The names were not final, but the choice matters. Without an explicit policy,
an old request can finish late and replace newer state.

The July notes added a `ttl` to automatic cogs. A keyed async cog with a TTL can
act like `useQuery`: keep a result for a time, reuse it for another watcher, and
fetch again after it expires. The runtime still needs a clear difference
between freshness time and lifetime. A value may be stale but kept, or fresh
but unused and ready for disposal.

Async cogs also need a standard way to report activity and errors. The sketches
use `.live` for work in flight and `.latestFailure` for the last error. They do
not settle whether the main cog keeps its last good value, falls back to its
initial value, or wraps data, loading, and error in one result type.

## A coherent turn

The telephone problem is the most important correctness issue that Cog needs to
solve. The intended answer is a runtime that owns the update schedule instead
of letting a chain of Dart streams race through the app.

A manual write should start a turn. During that turn, the runtime finds the
affected automatic cogs, recomputes them in dependency order, and records any
changed edges. Watchers and Flutter should see the settled result of the turn,
not each half-finished step.

Async work cannot make a whole turn wait forever. Starting a request, finishing
it, failing it, and canceling or ignoring it are separate events. Each event can
produce its own sound snapshot. The selected scheduler decides which finished
result is still allowed to write.

This is the direction implied by the Conveyor runtime and the complaint about
Subject streams. The notes do not give the full transaction algorithm. A full
spec still needs to define batching, dependency order, cycle errors, nested
writes, watcher timing, and what happens when a computation throws.

## Flutter use

Cog was always meant to support small Flutter rebuilds.

The early widget API was `useCog(cog, key: ...)`. It returns the current value
and rebuilds the calling widget when that cog changes. A widget can watch two
cogs without subscribing to the rest of a feature. A `Conveyor` widget gives
the subtree a runtime, much like other provider-based state tools.

This root runtime does not mean every piece of state must be global. Cog
declarations can live in any library, and the June sketch added `useNewCog` for
a cog created near a widget. A runtime should also be nestable so a subtree can
own and dispose its state.

The July notes proposed `useCog(..., once: true)` for a widget that needs a
value once but does not want later rebuilds. The same job may be clearer as a
plain `read`, but the need is valid.

Flutter context can provide a key, such as a ZIP code, while `useCog` selects
the matching value from a `CogBox`. This keeps entity identity close to the
widget that knows it.

Fine-grained subscriptions matter in a deep and expensive Flutter tree. Cog
should filter equal values and rebuild the smallest consumer, even when a large
feature owns the source data. Flutter rebuilds descendants when an ancestor
rebuilds, so placing the Cog consumer close to the leaf is an important part of
the performance model.

## Runtime identity, generation, and debug tools

The first Conveyor plan used generated `.g.dart` files. Generation would assign
an ID to each cog, register every machine, and add typed extensions for reads,
writes, and ops. It could also wrap an op with debug calls that record its name,
arguments, start, failure, and end.

In June 2023 I looked for a way to identify a top-level Cog without generation.
`StackTrace.current` can reveal the source line and surrounding function in the
Dart VM and JavaScript output. `dart:mirrors` was another thought, but it was not
usable because it hurts tree shaking and was banned in the target codebase.
`identityHashCode` also came up as a possible runtime tool.

Source locations from stack traces could make a prototype easy, but they are
not a sound long-term ID by themselves. Minification, source maps, moved lines,
and build modes can change them. Generated stable IDs are more work but give
debug tools better names. A final design could use object identity at runtime,
source locations for development hints, and generation only for stable labels
or write-boundary lints.

The debugger should be able to answer basic questions:

- Which op started this turn?
- Which manual cogs were written, and what were their old and new values?
- Which automatic cogs ran, in what order, and why?
- Which dependency edges were added or removed?
- Which values were filtered out as equal?
- Which async runs are active, stale, canceled, or failed?
- Which widgets or mechanisms were notified after the turn settled?

This is the Redux-style strength that Subject/BLoC never got to finish.

The March checklist also marked an escape hatch as needed. The notes do not say
exactly what it was. The final design should keep any escape hatch narrow and
make its use visible in debug history.

## Testing

The March 2023 test sketch used a `FakeConveyor`. A test could seed manual and
automatic cogs, make a write without sending an event, start mechanisms, call a
named op, and read the result for one key.

That supports a useful testing split:

- Test an automatic cog as a function of seeded dependencies.
- Test an op by calling it and checking its writes and service calls.
- Test a mechanism with a fake runtime and controlled turns or time.
- Test a widget with a local runtime and only the cogs it needs.
- Test the scheduler with overlapping async runs and out-of-order finishes.

Quiet writes are helpful during setup, but the API should make it hard to use
them in production by mistake.

The November notes also planned a bridge to the old Subject system. A Cog could
be converted to a Subject with `toSubject(cogtext)`, and a Cog could track an
old Subject with `c.linkSubject(subject)`. This would allow one feature at a
time to move to Cog.

## How the design changed over time

### 2022: the starting model

The [early BLoC notes](https://github.com/skeswa/notes/blob/master/incubator/work/2022-q2-bloc.md)
describe application state as a directed graph of small facts. Two journal
entries record useful ideas from existing Flutter and web tools. The
[February 2 entry](https://github.com/skeswa/notes/blob/master/journal/2022-02-02.md)
points to Recoil and its atom-based state model. The
[February 15 entry](https://github.com/skeswa/notes/blob/master/journal/2022-02-15.md)
notes that Flutter's `InheritedModel` lets a widget depend on one aspect of a
larger object and rebuild only when that aspect changes.

The goal at this point was still to explain and improve Ditto BLoC, not to build
Cog. The key ideas were already present: single sources of truth, declared
causes, easy graph growth, and small rebuilds.

### [March 10, 2023](https://github.com/skeswa/notes/blob/master/journal/2023-03-10.md): the first Cog sketch

The first named Cog API had `Cog.simple` for writable state and `Cog.fancy` for
computed or streaming state. A `use` function linked dependencies. A
`Mechanism` watched `isNiceOutside`, called a notification service, and used
`turn` to increment a manual count.

This draft already had conditional dependencies, async generators, side
effects, and extension methods as the app's write API.

### [March 14, 2023](https://github.com/skeswa/notes/blob/master/journal/2023-03-14.md): a class-based Machine

`WeatherMachine extends Machine` grouped cogs, derived values, methods, and an
`operate()` lifecycle. A context object could read, write, watch, call
`readPrevious()` for a prior value, and register cleanup.

The open work named keyed cogs, keyed mechanisms, hooks, Rx mapping choices,
and testing. Most of those ideas landed in the next sketch.

### [March 16, 2023](https://github.com/skeswa/notes/blob/master/journal/2023-03-16.md): top-level cogs and one Conveyor

The design moved cogs out of a class and into a plain Dart library. Generated
code registered the weather machine and added typed methods to the Conveyor.
`Cog.simple` and `Cog.complex` were top-level values.

This version added per-context state, context flowing through dependencies,
temporary links, async concurrency policies, a fake runtime for tests, a
Flutter `useCog` hook, and a root `Conveyor` widget. Mutations were called
maneuvers. Side effects were mechanisms.

### [March 29](https://github.com/skeswa/notes/blob/master/journal/2023-03-29.md) and [March 31, 2023](https://github.com/skeswa/notes/blob/master/journal/2023-03-31.md): the Conveyor write-up and the move from scope to key

The Conveyor write-up stated the goals and the machine metaphor. It compared
the design directly with Ditto Subject/BLoC, NgRx, Jotai, and Riverpod.

Feedback then exposed a problem with implicit context. Simple cogs could not say
which context they used, and explicit scope lists were hard to work with. The
next sketch replaced scope with typed keys, renamed writable and derived cogs
to manual and automatic, let keys flow through dependencies, and used explicit
keys only at a boundary.

There was also a short `driver` and `driven` experiment built around a
hook-style `self.state(...)` call. The journal rejects it almost at once and
moves on to manual and automatic cogs.

Maneuvers became levers. Writes became `turn`, `advance`, or `write`. The names
were moving, but the shape was getting smaller.

### [June 16, 2023](https://github.com/skeswa/notes/blob/master/journal/2023-06-16.md): Machina, ops, and identity

The project name changed to Machina. The API became `Cog.man`, `Cog.auto`, and
`Cog.proc`. Reads became `c.link`. The draft added first-class sync and async
ops, live-call state, latest-failure state, mechanisms, local `useNewCog`
derivations, and a way to keep the current value.

This was also the point where direct access felt dangerous. Cog values should
be read through a controller so dependencies and reads stay visible. Runtime
identity became a focus, with experiments using stack traces instead of
reflection or generation.

### [July 6](https://github.com/skeswa/notes/blob/master/journal/2023-07-06.md) and [July 23, 2023](https://github.com/skeswa/notes/blob/master/journal/2023-07-23.md): query behavior and no Machine class

Automatic cogs gained a proposed TTL to cover query caching. `useCog` gained a
one-time read option.

Later that month, the `Machine` class was dropped. A lint could limit writes to
the library that declared a manual cog. More lints would catch unsafe hook
control flow and late mechanism declarations.

### [September 14, 2023](https://github.com/skeswa/notes/blob/master/journal/2023-09-14.md): ARP and StateNotifier

Cog briefly became `Arp`, short for Algebraic effect, Reactive state, Primitive.
The sketch used `StateNotifier` as the manual state holder and kept a controller
that derived one value from another. This was more a naming and implementation
experiment than a new model.

The journal also links to a proposed Observable API and says it is the wrong
take, but it does not record why. There is not enough detail to turn that
reaction into a Cog rule.

### [November 30, 2023](https://github.com/skeswa/notes/blob/master/journal/2023-11-30.md): Cogtext and migration

The runtime became `Cogtext`. The notes named `CogController` and
`MechanismController`, changed initial values into callbacks, and made regular
extensions on `Cogtext` the home for named app functions.

This version kept TTL and async live state. It also added two-way bridges to the
old Subject system, which made a gradual migration possible.

### [January 20, 2026](https://github.com/skeswa/notes/blob/master/journal/2026-01-20.md): a smaller signals core

The latest sketch says plainly that Cog is an ergonomic signals design focused
on simplicity, correctness, and performance.

The surface is much smaller: `Cog.man` for one manual value, `Cog` for one
derived value, `CogBox` for a keyed family, `c.get` for dependency reads, and
`Cogtext.run` for a reaction. Ops, schedulers, debug hooks, and migration tools
are not shown, but the older notes still give them a place behind this smaller
front door.

The note also raises a new goal: test the same idea in Swift, not only Dart and
Flutter.

## The latest compact example

This is the January 2026 sketch with the nullable temperature type made
explicit:

```dart
late temperature = CogBox.man<double?, ZipCode>((c, zipCode) => null);

late user = Cog.man<User?>((c) => null);

late usersZipCode = Cog((c) {
  return c.get(user)?.zipCode;
});

late isNice = CogBox<bool, ZipCode>((c, zipCode) {
  final temp = c.get(temperature[zipCode]);
  return temp != null && temp > 68.0;
});

late shouldUserGoOutside = Cog((c) {
  final zipCode = c.get(usersZipCode);
  if (zipCode == null) {
    return false;
  }

  return c.get(isNice[zipCode]);
});

Cogtext.run((c) {
  if (c.get(shouldUserGoOutside)) {
    print('Go!');
  }
});
```

This example captures the part of Cog that seems most settled. Manual state is
rare. Derived state is plain code. Dependencies come from reads. Keyed state is
indexed like a collection. Reactions sit at the edge.

## A worked weather example

Weather was the running example in most of the old sketches. This version uses
the small 2026 surface while bringing back ops, keyed state, and reactions from
the earlier designs. The exact method names are still open.

The app stores the latest weather report and heat-advisory flag for each ZIP
code. Everything else is derived. The example assumes that the app already has
`ZipCode`, `WeatherService`, and `HeatAdvisory` types.

```dart
enum WeatherKind {
  clear,
  partlyCloudy,
  cloudy,
  rain,
  snow,
}

class Weather {
  final WeatherKind kind;
  final double temperatureF;

  const Weather({
    required this.kind,
    required this.temperatureF,
  });
}

late weatherService = Cog.man<WeatherService>((c) {
  return WeatherService();
});

late currentZipCode = Cog.man<ZipCode?>((c) => null);

late weather = CogBox.man<Weather?, ZipCode>((c, zipCode) => null);

late isHeatAdvisoryInEffect =
    CogBox.man<bool, ZipCode>((c, zipCode) => false);
```

`weather`, `isHeatAdvisoryInEffect`, and `currentZipCode` are manual because
they come from outside the state graph. The network reports the weather and
advisories. The location system reports the current ZIP code.

The rest of the graph is plain computation:

```dart
late isSunny = CogBox<bool, ZipCode>((c, zipCode) {
  final report = c.get(weather[zipCode]);

  return switch (report?.kind) {
    WeatherKind.clear || WeatherKind.partlyCloudy => true,
    _ => false,
  };
});

late isNiceOutside = CogBox<bool, ZipCode>((c, zipCode) {
  final report = c.get(weather[zipCode]);
  if (report == null) {
    return false;
  }

  final sunny = c.get(isSunny[zipCode]);
  if (!sunny) {
    return false;
  }

  final heatAdvisory = c.get(isHeatAdvisoryInEffect[zipCode]);

  return report.temperatureF > 60 &&
      report.temperatureF < 90 &&
      !heatAdvisory;
});

late isNiceOutsideHere = Cog((c) {
  final zipCode = c.get(currentZipCode);
  if (zipCode == null) {
    return false;
  }

  return c.get(isNiceOutside[zipCode]);
});
```

The early returns matter. When there is no weather report, `isNiceOutside` does
not need to read anything else. When it is cloudy, the heat-advisory value
cannot change the answer, so that dependency is not needed either. A runtime
with dynamic dependency tracking would remove links that the next run does not
use.

The app changes the manual cogs through a named op:

```dart
extension WeatherOps on Cogtext {
  Future<void> checkWeather(ZipCode zipCode) async {
    final service = read(weatherService);

    final (nextWeather, advisories) = await (
      service.weatherFor(zipCode),
      service.advisoriesFor(zipCode),
    ).wait;

    write(weather[zipCode], to: nextWeather);
    write(
      isHeatAdvisoryInEffect[zipCode],
      to: advisories.any((item) => item is HeatAdvisory),
    );
  }

  void useCurrentLocation(ZipCode zipCode) {
    write(currentZipCode, to: zipCode);
  }
}
```

This example assumes that writes made by one op are committed as one turn.
`isSunny` and `isNiceOutside` should recompute before watchers are notified.
The UI should never see the new weather report paired with the old advisory
flag.

A reaction can sit at the edge of the graph:

```dart
final niceWeatherNotification = Cogtext.run((c) {
  if (c.get(isNiceOutsideHere)) {
    alert('It is nice outside!');
  }
});
```

And a widget can subscribe to only one ZIP code:

```dart
class WeatherCard extends HookWidget {
  final ZipCode zipCode;

  const WeatherCard({
    super.key,
    required this.zipCode,
  });

  @override
  Widget build(BuildContext context) {
    final cogtext = useCogtext();
    final report = useCog(weather[zipCode]);
    final nice = useCog(isNiceOutside[zipCode]);

    return Column(
      children: [
        Text(report == null
            ? 'No weather report yet'
            : '${report.temperatureF.round()}°F'),
        Text(nice ? 'Go outside!' : 'Stay in.'),
        TextButton(
          onPressed: () => cogtext.checkWeather(zipCode),
          child: const Text('Check the weather'),
        ),
      ],
    );
  }
}
```

If the report for another ZIP code changes, this widget does not rebuild. If
the selected report changes but `isNiceOutside` stays equal, only the consumer
of the report needs to update. The runtime still records the op, both manual
writes, every derived cog that ran, and the reaction or widget that was
notified.

One call now shows most of the intended system:

1. The user calls `checkWeather(zipCode)`.
2. The op reads a service and starts two requests.
3. Both results are written in one turn.
4. Only the cogs for that ZIP code recompute.
5. Reactions and widgets see the settled state.

## What seems settled

The state model is a directed graph of small facts. Most state should be
derived, and manual state should sit at clear input points.

Dependencies should be recorded by reads through a controller. The runtime
should know why every automatic value ran.

Keyed state is a first-class need. `CogBox<T, K>` is the clearest form tried so
far.

Writes need an ownership rule even if there is no `Machine` class. Named
functions plus library lints are the leading answer.

Side effects should be kept out of derived cogs. A mechanism or reaction owns
them.

The runtime must control update order so observers see a sound snapshot. It
must also make async overlap an explicit choice.

Flutter should subscribe at the cog level and rebuild only the smallest useful
widget.

Debug history and good tests are part of the design, not extras to bolt on
later.

## What is still open

The public name is not final. Cog is the current name, Conveyor is a strong
name for the full runtime, Machina was used for a package, and Cogtext became
the latest runtime name.

The exact public types are also open. The notes try separate manual, automatic,
and procedural constructors, then collapse some of them. They do not decide
whether `Op` and `Mechanism` must be first-class values or can usually be plain
`Cogtext` callbacks.

Dependency tracking needs one clear rule. Dynamic links work well with early
returns and keyed loops. Hook-order rules are easier to implement in some
runtimes. Mixing both would be confusing.

The turn algorithm needs a written spec. Batching, nested writes, cycles, thrown
errors, watcher timing, and async completion all need exact behavior.

Keyed cogs need lifetime rules. TTL covers freshness, but not full cleanup.

Async data needs one standard surface for last good data, loading, failure,
retry, and cancellation. `.live` and `.latestFailure` are a start.

Stable identity is not settled. Code generation, source locations, and object
identity each solve a different part of the problem.

Write control through a lint is friendly, but the design should decide what is
also enforced at compile time or runtime when the lint is missing.

The runtime should support both global and local state without making their
lifetimes hard to see.

The Swift version needs study. Swift macros, property wrappers, actors, and
Observation may change the best surface even if the graph model stays the
same.

## A working definition

Cog is a small signals system for Dart, Flutter, and possibly Swift. A `Cog`
holds one value. An automatic Cog reads other Cogs and becomes their dependent.
A `CogBox` holds the same kind of Cog for many keys. A `Cogtext` owns values,
turns, reactions, async schedules, and debug history. The app changes manual
Cogs through named ops. Flutter listens only to the Cogs used by a widget.

The result should read like normal code, keep the whole state graph visible,
and never show the UI a half-finished state change.
